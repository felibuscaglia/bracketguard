Capabilities

Everything it checks — nothing it doesn't need.

A tight feature set, each one built to catch a real class of syntax bug with a precise, human-readable diagnostic.

( )

Balanced brackets

Validates (), [] and {} nesting with a stack — catching every mismatch, wrong-type close, and leftover opener.

" "

String awareness

Brackets inside "double-quoted" strings are ignored, and escaped quotes \" are handled correctly.

# _

Comment awareness

Everything after a # to end-of-line is skipped, so commented-out brackets never trigger false positives.

⌖

Precise error locations

Every failure reports an exact line and col, and points to the leftmost unclosed opener rather than the end of file.

→ )

Expected-closer hints

Mismatches tell you what was expected: expected ')' but found ']' — no guessing which bracket you actually meant.

</>

HTML / XML tags

The --tags mode validates open, close and self-closing tag nesting, catching malformed tags and crossed elements.

📊

Structure stats

--stats reports maximum nesting depth and per-type pair counts for any balanced file at a glance.

⏻

Scriptable exit codes

Returns 0 / 1 / 2 for pass / mismatch / file-error, so it drops straight into CI pipelines and git hooks.

∅

Pure standard library

No third-party packages. Just Python ≥ 3.9 and the stdlib — install in seconds, audit in minutes.

The algorithm

One pass. One stack. Exact answers.

bracketguard reads the file a single character at a time, pushing openers onto a hand-written stack and matching each closer against the top. Watch it run:

01

Scan left to right

Iterate every character once — tracking line & column as it goes.

02

Push each opener

An opener is placed on the stack together with its exact position.

03

Match each closer

Pop the top and confirm it's the correct partner — or fail with a precise diagnostic.

04

Verify an empty stack

Anything still on the stack at EOF is an unclosed opener, reported at its origin.

Under the hood

Clean, layered, and readable by design.

Three small modules with a single responsibility each — the kind of separation that keeps a codebase testable and honest as it grows.

stack.pydata structure

A singly-linked-list Stack, written from scratch — no list shortcuts.

  • Each Node stores a value and its (col, line) position
  • O(1) push / pop / is_empty
  • Positions travel with the data for exact diagnostics
checker.pycore engine

The scanning logic and result model, fully decoupled from I/O.

  • Frozen CheckResult dataclass — immutable outcomes
  • ErrorKind enum: 4 well-named failure modes
  • Two engines: check() & check_tags()
cli.pyinterface

A thin argparse layer that formats results for humans.

  • check subcommand with --stats / --tags
  • Message formatting isolated from detection
  • Installed as a real console script entry point
bracketguard/checker.py — the matching corepython
for index, char in enumerate(content):
    # ... newline / string / comment handling omitted ...
    elif char in OPENER_TO_CLOSER:
        stack.push(value=char, line=line, col=col)   # remember where it opened
        curr_depth += 1
    elif char in CLOSER_TO_OPENER:
        node = stack.pop()
        opener = node.value if node is not None else None
        if opener is None or CLOSER_TO_OPENER[char] != opener:
            return CheckResult.failure(
                ErrorKind.UNEXPECTED_CLOSER, line, col,
                found=char,
                expected=OPENER_TO_CLOSER[opener] if opener else None,
            )
        pair_counts[opener] += 1
